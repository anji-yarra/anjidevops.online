Module Fundamentals
What modules are and why they matter
Definition
What Are Terraform Modules?
Container for related infrastructure resources
›

A Terraform module is a folder containing Terraform files that define infrastructure resources as a reusable, self-contained unit. It's a way to package related resources (VPC, subnets, security groups) into a single component you can use across multiple projects.

Key concept: Modules are like functions in programming. You write a function once, then call it multiple times with different parameters. Terraform modules work the same way—define infrastructure once in a module, then use it in many projects.
Module concept visualization
# Without modules (repetitive) # Project 1 - main.tf resource "aws_vpc" "vpc" { ... } resource "aws_subnet" "public" { ... } resource "aws_internet_gateway" "igw" { ... } # Project 2 - main.tf (same code again!) resource "aws_vpc" "vpc" { ... } resource "aws_subnet" "public" { ... } resource "aws_internet_gateway" "igw" { ... } # With modules (DRY principle) # modules/vpc/main.tf resource "aws_vpc" "vpc" { ... } resource "aws_subnet" "public" { ... } resource "aws_internet_gateway" "igw" { ... } # Project 1 - main.tf module "vpc" { source = "../modules/vpc" } # Project 2 - main.tf module "vpc" { source = "../modules/vpc" }
ReusablePackagedSelf-contained
Benefits
Why Use Modules?
The practical advantages
›

Modules provide major benefits: code reusability, maintainability, consistency, organization, and testing. Without modules, you duplicate code, make updates difficult, and create inconsistencies. Modules solve all these problems.

Real example: You manage 5 AWS projects, each needing identical VPC setup (public/private subnets, NAT Gateway, security groups). Without modules: update one security group setting = fix it in 5 places. With modules: update once in the module, all 5 projects inherit the change instantly.
Benefits comparison
WITHOUT MODULES Code Reusability: ❌ Copy-paste 200+ lines 5 times Maintainability: ❌ Update code in 5 places Organization: ❌ 1000+ line monolithic file Consistency: ❌ Each person configures differently Testing: ❌ Hard to test individual pieces Time to Scale: ❌ Complex projects = messy code WITH MODULES Code Reusability: ✅ Write once, use everywhere Maintainability: ✅ Update module, affects all uses Organization: ✅ Logical, focused components Consistency: ✅ Same configuration every time Testing: ✅ Test modules independently Time to Scale: ✅ Compose modules for complexity
ReusabilityConsistencyScalability

Real-world comparisons
›

Think of Terraform modules like construction blueprints. A blueprint is a design you create once, then use to build multiple houses. Each house gets the same layout but can customize details (size, color, materials).

The analogy: Blueprint = module. Building a house = creating infrastructure. Customizing details = module variables. This mental model makes modules intuitive.

Timing
When Should You Use Modules?
Practical guidance on module adoption
›

Use modules when you have reusable infrastructure or multiple projects. Start with modules from day one if building multiple environments or projects. Even a single project benefits from modular structure.

Growth pattern: Single project → organize with modules. Two projects → extract common module. Many projects → shared module library. Enterprise → module registry with governance.
Decision tree
SINGLE PROJECT, SIMPLE (< 10 resources) ✓ Can keep in single main.tf → But modules still improve organization SINGLE PROJECT, COMPLEX (> 10 resources) ✓ MUST USE MODULES networking/ - VPC, subnets, gateways compute/ - EC2, ASG, load balancers database/ - RDS, backups security/ - IAM, security groups MULTIPLE PROJECTS (SAME INFRASTRUCTURE) ✓ DEFINITELY USE MODULES Each project calls shared modules with different variables One source of truth for infrastructure design ENTERPRISE (MANY TEAMS, MANY PROJECTS) ✓ USE MODULE REGISTRY Published modules with versioning Governance and standards enforcement Team reuse at scale

Module Structure & Organization
How modules are organized on disk
Layout
Module Directory Structure
Organizing files within a module
›

A module is just a directory with Terraform files. The standard structure includes main.tf (resources), variables.tf (inputs), outputs.tf (returns), and optionally README.md (documentation) and terraform.tfvars (defaults).

Standard convention: Following this structure makes modules predictable and easy to understand. Other Terraform developers expect this layout. It's not required, but it's the community standard for good reasons.
Standard module structure
project/ ├── main.tf # Root module config ├── terraform.tfvars ├── outputs.tf ├── variables.tf └── modules/ ├── vpc/ │ ├── main.tf # VPC resources │ ├── variables.tf # Input variables │ ├── outputs.tf # Return values │ └── README.md # Documentation │ ├── rds/ │ ├── main.tf │ ├── variables.tf │ ├── outputs.tf │ └── README.md │ └── security/ ├── main.tf ├── variables.tf ├── outputs.tf └── README.md EACH MODULE IS SELF-CONTAINED All files for VPC module → vpc/ directory All files for RDS module → rds/ directory Easy to find, understand, reuse
OrganizationConventionStandard
Files
Purpose of Each Module File
What goes in each .tf file
›

Each file in a module serves a specific purpose. main.tf defines resources, variables.tf defines inputs, outputs.tf defines return values. This separation keeps code organized and makes modules easier to understand.

Separation of concerns: Don't mix resource definitions with variable declarations—keep them separate. This makes the code scannable: "I want to see inputs" → look at variables.tf. "I want to see what's created" → look at main.tf.
File purposes
main.tf - Resource definitions resource "aws_vpc" "this" { cidr_block = var.cidr_block enable_dns_hostnames = var.enable_dns } resource "aws_subnet" "public" { vpc_id = aws_vpc.this.id cidr_block = var.public_subnet_cidr availability_zone = var.availability_zone } variables.tf - Input parameters variable "cidr_block" { description = "CIDR block for VPC" type = string default = "10.0.0.0/16" } variable "public_subnet_cidr" { description = "CIDR block for public subnet" type = string } variable "availability_zone" { description = "AZ for subnet" type = string } outputs.tf - Return values output "vpc_id" { description = "ID of the VPC" value = aws_vpc.this.id } output "subnet_id" { description = "ID of public subnet" value = aws_subnet.public.id } README.md - Documentation # VPC Module Creates a VPC with configurable subnets. ## Usage module "vpc" { source = "../modules/vpc" cidr_block = "10.0.0.0/16" }

Sources
Module Sources (Where to Load From)
Local, Git, Registry, S3
›

Modules can be loaded from multiple sources: local filesystem (relative paths), Git repositories (remote), Terraform Registry (official modules), S3 (private storage), and more. Source flexibility enables code sharing across teams and organizations.

Flexibility advantage: Start with local modules during development. As you mature, move to Git repos for version control. Eventually use Registry for public sharing or S3 for private enterprise use.
Different module sources
LOCAL - During development module "vpc" { source = "../modules/vpc" # Relative path to local module } GIT - Team shared repos module "vpc" { source = "git::https://github.com/company/tf-modules.git//vpc?ref=v1.0.0" # Git repo with versioning } TERRAFORM REGISTRY - Official public modules module "vpc" { source = "terraform-aws-modules/vpc/aws" version = "~> 5.0" # Published, maintained, documented } S3 - Private enterprise modules module "vpc" { source = "s3::https://s3.amazonaws.com/my-bucket/modules/vpc.zip" # Company-internal modules } EXAMPLE: Real-world mix module "custom_vpc" { source = "../modules/vpc" # Local, under development } module "security_groups" { source = "git::https://github.com/company/modules.git//security?ref=v2.1" # Team standard security configs } module "rds" { source = "terraform-aws-modules/rds/aws" # Official AWS module version = "6.0" }
SourcesLocalGitRegistry
Root
Root Module vs Child Modules
Understanding the module hierarchy
›

Every Terraform configuration has a root module (the directory where you run terraform commands). Child modules are modules called by the root module. The root module orchestrates everything, child modules provide components.

Hierarchy: Root module is the entry point. It defines variables that users pass in, calls child modules, and produces outputs. Child modules are reusable components. This hierarchy enables clean separation of concerns.
Root vs child modules
PROJECT DIRECTORY (Root Module) project/ ├── main.tf # Root module - orchestrates everything ├── variables.tf # Root module inputs from user ├── outputs.tf # Root module outputs to user └── modules/ ├── vpc/ # Child module - VPC component ├── rds/ # Child module - Database component └── security/ # Child module - Security component ROOT MODULE main.tf - Orchestrates module "network" { source = "./modules/vpc" cidr = var.network_cidr } module "database" { source = "./modules/rds" subnet = module.network.subnet_id } VPC CHILD MODULE main.tf - Component resource "aws_vpc" "this" { cidr_block = var.cidr_block } resource "aws_subnet" "this" { vpc_id = aws_vpc.this.id # ... } HIERARCHY User runs: terraform apply ↓ Root module gets user variables ↓ Root module calls child modules with values ↓ Child modules create actual infrastructure ↓ Child modules return outputs to root ↓ Root module returns final outputs to user
HierarchyRootChildOrchestration

Module Variables & Inputs
Making modules flexible and reusable
Inputs
Module Input Variables
Parameterize modules for flexibility
›

Input variables make modules flexible. Instead of hardcoding values, define variables that callers pass in. This way, one module can create different infrastructure based on inputs. Variables are how modules accept parameters like function arguments.

Function analogy: In programming, functions take parameters. Terraform variables are module parameters. function(name, age) vs module with variable "name", variable "age". Same concept.
Module variables
modules/vpc/variables.tf variable "vpc_cidr" { description = "CIDR block for VPC" type = string default = "10.0.0.0/16" } variable "environment" { description = "Environment name" type = string # No default - required! } variable "enable_nat" { description = "Enable NAT Gateway?" type = bool default = true } variable "tags" { description = "Tags to apply" type = map(string) default = {} } modules/vpc/main.tf - USE variables resource "aws_vpc" "this" { cidr_block = var.vpc_cidr # Use variable tags = merge( var.tags, { Name = "${var.environment}-vpc" } ) } main.tf - ROOT MODULE provides values module "prod_vpc" { source = "./modules/vpc" vpc_cidr = "10.0.0.0/16" environment = "production" enable_nat = true tags = { Project = "MyApp" Owner = "Platform Team" } } module "dev_vpc" { source = "./modules/vpc" vpc_cidr = "10.1.0.0/16" # Different CIDR environment = "development" enable_nat = false # No NAT for dev tags = { Project = "MyApp" Owner = "Dev Team" } }
VariablesParametersFlexibility
Types
Variable Types & Validation
Ensuring correct inputs
›

Variables have types: string, number, bool, list, map, etc. Terraform validates types, catching errors early. Add validation rules to ensure inputs are reasonable (CIDR blocks are valid, numbers are in range, etc.).

Type safety: Without types, you might pass "abc" when a number is expected. With types, Terraform catches this immediately. Validation adds business logic: "port must be 1-65535", "environment must be prod/staging/dev".
Variable types and validation
Basic types variable "instance_name" { type = string # Text } variable "instance_count" { type = number # Integer or float } variable "enable_monitoring" { type = bool # true/false } Complex types variable "availability_zones" { type = list(string) # ["us-east-1a", "us-east-1b"] } variable "tags" { type = map(string) # {env="prod", team="platform"} } variable "instance_config" { type = object({ instance_type = string root_volume_size = number encryption = bool }) } WITH VALIDATION variable "port" { type = number validation { condition = var.port >= 1 && var.port <= 65535 error_message = "Port must be 1-65535" } } variable "environment" { type = string validation { condition = contains( ["dev", "staging", "prod"], var.environment ) error_message = "Environment must be dev, staging, or prod" } } variable "cidr_block" { type = string validation { condition = can(cidrhost(var.cidr_block, 0)) error_message = "CIDR block must be valid" } }
TypesValidationSafety
Defaults
Defaults and Required Variables
When to require input vs provide defaults
›

Variables with defaults are optional. Variables without defaults are required. Choose wisely: required variables force users to be explicit (good for important settings), defaults simplify common cases (good for advanced options).

Strategy: Critical settings (environment, region) should be required. Advanced options (monitoring level, backup frequency) should have sensible defaults. This balances safety with usability.
Defaults vs required
REQUIRED - User MUST provide variable "environment" { description = "Environment (prod/staging/dev)" type = string # NO default - required! } variable "database_name" { description = "Database name" type = string # NO default - required! } OPTIONAL - Has sensible default variable "instance_type" { description = "EC2 instance type" type = string default = "t3.micro" # Default for testing } variable "enable_encryption" { description = "Enable encryption?" type = bool default = true # Default secure } variable "tags" { description = "Tags to apply" type = map(string) default = {} # Default empty } USAGE module "app" { source = "./modules/app" # REQUIRED - must provide environment = "production" database_name = "myapp_db" # OPTIONAL - use defaults if not provided instance_type = "t3.large" # Override default # enable_encryption defaults to true # tags defaults to empty }
DefaultsRequiredDesign
Sensitive
Sensitive Variables
Handling secrets safely
›

Mark sensitive variables with sensitive=true to prevent Terraform from displaying them in logs or CLI output. This protects passwords, API keys, and other secrets from being exposed in console output or state files.

Security best practice: Even though Terraform masks output, the real protection is using external secret management (AWS Secrets Manager, HashiCorp Vault). Mark variables sensitive=true as an additional safeguard.
Sensitive variables
modules/rds/variables.tf variable "database_password" { description = "RDS master password" type = string sensitive = true # Hide from output! } variable "api_key" { description = "External API key" type = string sensitive = true } variable "database_name" { description = "Database name" type = string # NOT sensitive - it's not secret } USAGE - Supply sensitive values via # Option 1: terraform.tfvars (gitignore this!) database_password = "very-secret-password-here" api_key = "sk_prod_1234567890" # Option 2: Environment variables export TF_VAR_database_password="secret" export TF_VAR_api_key="key" terraform apply # Option 3: AWS Secrets Manager (best practice) variable "database_password" { type = string sensitive = true default = data.aws_secretsmanager_secret_version.db_password.secret_string } data "aws_secretsmanager_secret_version" "db_password" { secret_id = "prod/rds/password" }

Module Outputs
Returning values from modules
Outputs
Module Outputs Basics
Returning values to callers
›

Module outputs return values that other modules or the root module can use. Define outputs in outputs.tf, then reference them with module.name.output_name. Outputs are how modules communicate results back.

Function analogy: In programming, functions return values. Terraform modules return values via outputs. This enables composition: one module's output becomes another's input, creating dependencies.
Module outputs
modules/vpc/outputs.tf output "vpc_id" { description = "ID of the VPC" value = aws_vpc.this.id } output "public_subnet_id" { description = "ID of public subnet" value = aws_subnet.public.id } output "nat_gateway_ip" { description = "Elastic IP of NAT Gateway" value = aws_eip.nat.public_ip } main.tf - Root module calls VPC module module "vpc" { source = "./modules/vpc" vpc_cidr = "10.0.0.0/16" } main.tf - Use VPC module outputs module "rds" { source = "./modules/rds" # Pass VPC output as RDS input! subnet_id = module.vpc.public_subnet_id vpc_id = module.vpc.vpc_id } main.tf - Return values to user output "vpc_id" { description = "VPC ID to use in other configs" value = module.vpc.vpc_id } output "nat_ip" { description = "NAT Gateway IP for firewall rules" value = module.vpc.nat_gateway_ip } USAGE terraform apply Outputs: vpc_id = "vpc-12345" nat_ip = "54.1.2.3" # Use output in shell scripts VPC_ID=$(terraform output -raw vpc_id) NAT_IP=$(terraform output -raw nat_ip)

Types
Output Types and Sensitivity
What outputs can return
›

Outputs can return any value type: strings, numbers, lists, maps, objects, even sensitive values. Mark outputs sensitive=true if they contain passwords or API keys. Terraform will automatically determine output type based on the value.

Flexibility: Outputs aren't limited to simple strings. Return complex data structures so modules can share complete information. For example, an RDS module might return the database connection string, endpoint, port, username separately.
Various output types
STRING OUTPUT output "database_endpoint" { description = "RDS endpoint" value = aws_db_instance.this.endpoint } NUMBER OUTPUT output "instance_count" { description = "Number of instances created" value = aws_autoscaling_group.this.desired_capacity } BOOLEAN OUTPUT output "encryption_enabled" { description = "Is encryption enabled?" value = aws_s3_bucket_server_side_encryption_configuration.this.rules[0].apply_server_side_encryption_by_default.sse_algorithm != "" } LIST OUTPUT output "instance_ids" { description = "IDs of all instances" value = aws_instance.this[*].id } MAP OUTPUT output "instance_ips" { description = "Map of instance names to IPs" value = { for inst in aws_instance.this : inst.tags.Name => inst.private_ip } } OBJECT (Complex) OUTPUT output "database_config" { description = "Complete database configuration" value = { endpoint = aws_db_instance.this.endpoint port = aws_db_instance.this.port database = aws_db_instance.this.name username = aws_db_instance.this.username } } SENSITIVE OUTPUT (password) output "database_password" { description = "Database password" value = aws_db_instance.this.password sensitive = true # Won't display in console } USAGE - Access outputs # In root module module "database" { source = "./modules/rds" } resource "some_resource" "this" { endpoint = module.database.database_endpoint password = module.database.database_password }

Doc
Documenting Outputs
Clear descriptions and examples
›

Always describe outputs clearly. Users need to know what each output contains and how to use it. Good descriptions prevent confusion and misuse. Add examples in README.md showing common usage patterns.

Documentation matters: A user sees terraform output and gets "sg-abc123". Without description, they don't know it's a security group. With description "Security group ID for web tier", they immediately understand what it is and how to use it.
Well-documented outputs
BAD - No description output "vpc_id" { value = aws_vpc.this.id } output "subnet_ids" { value = aws_subnet.this[*].id } GOOD - Clear description output "vpc_id" { description = "ID of the created VPC. Use this when creating resources that must connect to this VPC." value = aws_vpc.this.id } output "private_subnet_ids" { description = "List of private subnet IDs. Pass these to RDS subnet group for database deployment." value = aws_subnet.private[*].id } output "nat_gateway_ip" { description = "Public IP address of NAT Gateway. Add this to firewall whitelists for outbound access." value = aws_eip.nat.public_ip } README.md - Usage examples ## Outputs - **vpc_id**: VPC identifier. Example: `vpc-12345abc` - **private_subnets**: Private subnet IDs for database placement - **nat_ip**: NAT Gateway IP for firewall rules (e.g., 54.1.2.3) ## Example Usage module "network" { source = "./modules/vpc" } # Use outputs in other modules module "database" { source = "./modules/rds" subnet_ids = module.network.private_subnet_ids vpc_id = module.network.vpc_id } # Display outputs after apply terraform output vpc_id terraform output -json nat_ip

Composition
Module Composition
Building complex infrastructure from simple modules
›

Compose modules by calling multiple modules in your root configuration. Each module handles one concern (VPC, RDS, security), then you wire them together. This creates clean, maintainable infrastructure code that scales.

Separation of concerns: Keep modules focused. A VPC module creates VPC infrastructure only. An RDS module creates database only. A security module handles security groups only. This makes each module testable and reusable.
Module composition example
main.tf - Compose multiple modules # Step 1: Create networking module "networking" { source = "./modules/vpc" cidr_block = "10.0.0.0/16" environment = var.environment } # Step 2: Create security groups (depends on VPC) module "security" { source = "./modules/security" vpc_id = module.networking.vpc_id environment = var.environment } # Step 3: Create database (depends on VPC & security) module "database" { source = "./modules/rds" subnet_ids = module.networking.private_subnet_ids security_group_id = module.security.rds_security_group_id environment = var.environment } # Step 4: Create app servers (depends on all above) module "app" { source = "./modules/app" subnet_ids = module.networking.public_subnet_ids security_group_id = module.security.app_security_group_id database_endpoint = module.database.endpoint environment = var.environment } # Step 5: Return final outputs output "app_load_balancer_dns" { value = module.app.alb_dns_name } output "database_endpoint" { value = module.database.endpoint sensitive = true } BENEFITS OF COMPOSITION ✓ Each module has single responsibility ✓ Modules are independently testable ✓ Easy to reuse modules in other projects ✓ Changes to one module don't break others ✓ Clear data flow through outputs/inputs

Versioning
Module Versioning & Stability
Managing module updates safely
›

When modules live in Git repos, use Git tags for versioning (v1.0.0, v1.1.0, v2.0.0). Callers pin to specific versions to ensure stability. Use semantic versioning: MAJOR.MINOR.PATCH. Update minor version for new features, patch for bug fixes, major for breaking changes.

Stability matters: Without versioning, module updates could break existing infrastructure. Pinning versions lets teams update at their own pace. Semantic versioning tells users if updates are safe (patch, minor) or require attention (major).
Module versioning
GIT TAG YOUR MODULES git tag -a v1.0.0 -m "Initial release" git tag -a v1.1.0 -m "Add monitoring support" git tag -a v2.0.0 -m "Breaking change: variables renamed" git push --tags CALLERS PIN TO VERSION module "vpc" { source = "git::https://github.com/company/tf-modules.git//vpc?ref=v1.1.0" # Pin to v1.1.0 - stays on that version } TERRAFORM REGISTRY VERSIONING module "vpc" { source = "terraform-aws-modules/vpc/aws" version = "~> 5.0" # Allow 5.x.x, not 6.x.x (major) } module "rds" { source = "terraform-aws-modules/rds/aws" version = "6.1" # Exact version 6.1.x } SEMANTIC VERSIONING v1.0.0 = first release v1.1.0 = backward compatible feature (safe to update) v1.1.1 = bug fix (safe to update) v2.0.0 = breaking change (requires action before updating!) UPDATE STRATEGY ✓ Always pin module versions ✓ Review changelog before upgrading ✓ Test in non-prod before applying major versions ✓ Document why each module version is used

Testing
Testing Terraform Modules
Ensuring modules work correctly
›

Test modules with Terratest (Go testing framework for Terraform) or terraform validate/plan. Create test configurations that use the module with various inputs. Verify outputs are correct and resources are created properly. Good tests prevent breaking changes from reaching production.

Why test: Infrastructure changes are high-impact. A small bug in a module could affect dozens of deployments. Testing catches issues before production. It also documents expected behavior.
Testing modules
BASIC: terraform validate cd modules/vpc terraform init terraform validate INTERMEDIATE: terraform plan test # test/main.tf - test configuration module "vpc_test" { source = ".." # Parent directory (module under test) cidr_block = "10.0.0.0/16" environment = "test" } # Run plan cd test terraform plan -out=tfplan ADVANCED: Terratest (Go) // test_vpc_module.go package test import ( "testing" "github.com/gruntwork-io/terratest/modules/terraform" "github.com/stretchr/testify/assert" ) func TestVpcModule(t *testing.T) { terraformOptions := &terraform.Options{ TerraformDir: "../examples/vpc_example", } defer terraform.Destroy(t, terraformOptions) terraform.InitAndApply(t, terraformOptions) vpcId := terraform.Output(t, terraformOptions, "vpc_id") assert.NotEmpty(t, vpcId) } TEST CHECKLIST ✓ Validate syntax (terraform validate) ✓ Plan with minimal inputs (required variables only) ✓ Plan with all variables (test all options) ✓ Verify all outputs exist and have values ✓ Test variable validation (invalid inputs fail) ✓ Test with different variable combinations ✓ Verify security (no hardcoded secrets) ✓ Check dependencies between resources

Best Practices
Module Best Practices
Proven patterns for production modules
›

Follow best practices: keep modules focused (one responsibility), use clear naming, document thoroughly, validate inputs, handle defaults wisely, make outputs comprehensive, version everything, and test systematically. These practices ensure modules are robust, maintainable, and production-ready.

Production mindset: Someone else will use your module. Write it as if you won't be around to explain it. Clear names, complete documentation, and validation go a long way.
Best practices checklist
MODULE DESIGN ✓ Single responsibility (one thing, do it well) ✓ Clear, intuitive variable names ✓ Required variables for critical settings ✓ Sensible defaults for optional settings ✓ Comprehensive outputs (all useful values) ✓ Input validation (catch errors early) ✓ Security by default (encryption, restricted access) CODE ORGANIZATION ✓ main.tf - Resources ✓ variables.tf - Inputs ✓ outputs.tf - Return values ✓ locals.tf - Local variables ✓ versions.tf - Provider versions ✓ README.md - Documentation ✓ examples/ - Usage examples ✓ tests/ - Test configurations DOCUMENTATION ✓ Clear README with usage example ✓ Description for every variable ✓ Description for every output ✓ Comments for complex logic ✓ Examples of different configurations ✓ Troubleshooting section QUALITY ✓ Validate syntax (terraform validate) ✓ Test with multiple configurations ✓ Pin provider versions ✓ Pin module versions when calling ✓ Version module with Git tags ✓ Run linting (tflint) ✓ Security scanning (tfsec) SECURITY ✓ No hardcoded secrets ✓ Mark sensitive variables ✓ Restrict IAM policies to minimum needed ✓ Enable encryption by default ✓ Validate CIDR blocks and IPs ✓ Audit logging for sensitive resources EXAMPLE: PRODUCTION-READY MODULE modules/database/ ├── main.tf # RDS instance with security defaults ├── variables.tf # Validated inputs with docs ├── outputs.tf # All useful connection details ├── locals.tf # Computed values ├── versions.tf # Provider version constraints ├── README.md # Complete documentation ├── examples/ │ ├── basic/ # Minimal config example │ ├── advanced/ # With all options │ └── multi-az/ # Multi-AZ example └── tests/ ├── validate_test.tf ├── basic_test.tf └── security_test.tf
