HTTP Error Codes Complete Guide

Every status code from 1xx to 5xx — what they mean, when they fire, and how to handle them. With real-world AWS and DevOps examples.

HTTP status codes are the language of the web. Every time a browser or API client makes a request, the server responds with a 3-digit code. As a Cloud & DevOps engineer, you'll debug these daily — in ALB access logs, CloudWatch alarms, and Nginx error logs. Click any card to expand full details and real examples.

1xx
Informational
Request received · processing continues
100
Continue
Server received headers, client should proceed with body
›

Sent when the server has received the request headers and the client should proceed to send the request body. Used when sending large files — the client checks the server is ready before uploading.

Real World Example
POST /upload HTTP/1.1
Expect: 100-continue

→ 100 Continue
→ Client now sends the file body

101
Switching Protocols
Server agrees to switch protocol — most common for WebSockets
›

The server agrees to upgrade the protocol. Most commonly seen when upgrading from HTTP to WebSockets — the connection becomes a persistent, two-way channel.

WebSocket Handshake
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade

→ 101 Switching Protocols
→ Upgrade: websocket

102
Processing
Server is processing — no response yet (WebDAV)
›

A WebDAV extension code. Indicates the server has received and is processing the request but no response is available yet. Prevents the client from timing out on long operations.

WebDAVLong operations
2xx
Success
Request received, understood, and accepted
200
OK
Standard success — request completed successfully
›

The standard success response. Your ALB health checks must see 200 from EC2 targets for them to be marked Healthy. GET returns the resource, POST returns result of action.

AWS — ALB Health Check
ALB Target Health Check → 200 OK
EC2 instance marked: HEALTHY ✓

201
Created
Success — new resource was created
›

Returned after a POST successfully creates a resource. Response typically includes a Location header pointing to the new resource's URL.

204
No Content
Success — but no body to return
›

The server successfully processed the request but is not returning any content. Used for DELETE operations or PUT updates where you don't need to return the full resource back.

DELETE Example

→ 204 No Content

Partial Content
Only part of the resource returned — Range request
›

Used when the client sends a Range header. Common in S3 byte-range reads, video streaming, and download resumption.

3xx
Redirection
Further action needed to complete the request
301
Moved Permanently
Resource permanently moved — browsers cache this
›

The resource has permanently moved. Browsers cache it. In AWS, you'll configure 301 on ALB listener rules to force HTTP → HTTPS redirects.

ALB HTTP → HTTPS Redirect
ALB Listener (Port 80):
Action: Redirect to HTTPS
Status Code: 301

GET http://www.anjidevops.online
→ 301 → https://anjidevops.online
SEOALB redirectHTTP→HTTPS
302
Found (Temporary Redirect)
Temporarily at a different URL — don't cache
›

Temporary redirect — the original URL is still valid. Browsers don't cache this. Use for maintenance pages, A/B testing, or temporary rerouting.

TemporaryA/B testingMaintenance mode
304
Not Modified
Cached version still valid — use cache, no body sent
›

"Your cached copy is still fresh, use it." No body is sent, saving bandwidth. CloudFront uses this extensively for cache validation via ETag and If-None-Match headers.

CloudFront Cache Validation
GET /style.css
If-None-Match: "abc123"

→ 304 Not Modified
(no body — client uses cached copy)
CloudFrontETagCacheBandwidth
307
Temporary Redirect
Like 302 but HTTP method MUST NOT change
›

Temporary redirect that guarantees the HTTP method won't change. If a POST is redirected, some browsers change to GET with 302. 307 prevents this — POST stays POST.

POST safeTemporaryMethod preserved
308
Permanent Redirect
Like 301 but HTTP method MUST NOT change
›

Permanent redirect that preserves the HTTP method. The modern, stricter version of 301. Ensures POST stays POST even after a permanent move.

PermanentPOST safeModern
4xx
Client Errors
The request contains bad syntax or cannot be fulfilled
400
Bad Request
Malformed request — server cannot process it
›

The server cannot process due to invalid syntax — malformed JSON, missing required fields, invalid query params. The client must fix the request before retrying.

Invalid JSON Body

{"region": "ap-south-1", "count": } ← broken

→ 400 Bad Request

401
Unauthorized
Authentication required — who are you?
›

This is about authentication, not authorization (despite the name). Client must authenticate. Common with expired JWT tokens, missing API keys, or invalid AWS credentials.

Expired Token

→ 401 Unauthorized

403
Forbidden
Authenticated but not authorized — we know you, but NO
›

The client is authenticated but lacks permission. In AWS this is very common — IAM policy denials, S3 bucket policies. Key difference from 401: re-authenticating won't help.

AWS S3 Access Denied

404
Not Found
The most famous one — resource doesn't exist
›

The server can't find the requested resource. If your ALB target returns 404, check your Nginx config and file root path — most common deployment mistake.

Wrong Nginx Root
Nginx root: /var/www/html/
File exists: /usr/share/nginx/html/index.html

→ 404 Not Found
Fix: update root path in nginx.conf

Method Not Allowed
HTTP method not supported for this endpoint
›

The endpoint exists, but doesn't support the HTTP method used. Response includes an Allow header listing valid methods.

429
Too Many Requests
Rate limit exceeded — slow down
›

The client has sent too many requests. AWS API Gateway returns 429 when throttling. Response includes Retry-After header. Key for DDoS mitigation and API protection.

API Gateway Throttle
GET /api/data (1000 req/sec, limit: 100)

→ 429 Too Many Requests

Server Errors
Server failed to fulfil a valid request — not the client's fault
500
Internal Server Error
Unexpected server condition — generic catch-all error
›

The server hit an unexpected condition. Could be unhandled exception, DB failure, or memory overflow. Check CloudWatch logs immediately — set up alarms for 5XX counts on ALB.

Service Unavailable
Server is down or overloaded — your biggest production alert
›

In AWS: all ALB targets fail health checks → ALB returns 503 to all requests. This is your most critical production alert. Set CloudWatch alarm on HealthyHostCount = 0.

ALB No Healthy Targets

504
Gateway Timeout
Upstream didn't respond in time — ALB idle timeout exceeded
›

In AWS: ALB idle timeout is 60s by default. If EC2 takes longer than 60s to respond, ALB returns 504. Fix: increase ALB idle timeout or optimize the slow query.
