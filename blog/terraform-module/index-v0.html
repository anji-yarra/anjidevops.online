What Are Terraform Modules?

A Terraform module is a reusable container for multiple resources that are used together. Think of it as a building block that groups related infrastructure code into a single package you can use multiple times.

Simple Definition: A module is a folder containing Terraform files that defines a set of infrastructure resources as a single unit.

Real-World Analogy

Imagine you're building a house. Without modules, you'd build each house from scratch, writing down every detail (brick by brick, room by room). With modules, you create a "blueprint" once, then use it to build multiple houses without repeating the work.

Same concept with Terraform modules:

  • 🏠 Without modules: Write VPC configuration in every project
  • ✅ With modules: Create a VPC module once, use it in 10 projects

Why Use Terraform Modules?

Benefit Without Modules With Modules
Code Reusability Copy-paste same code everywhere ❌ Write once, use everywhere ✅
Maintainability Update code in 10 places 😞 Update module, affects all uses ✅
Organization One huge file (1000+ lines) 🤯 Organized into logical modules ✅
Consistency Each person configures differently Same configuration every time ✅
Testing Hard to test individual parts Test modules independently ✅
Scaling Complex infrastructure = messy code Compose modules for complexity ✅
Real-world example: If you have 5 AWS projects needing identical VPC setup (public/private subnets, NAT Gateway, etc.), without modules you'd copy 200+ lines of code 5 times. With modules, write once, use 5 times!

Understanding Module Structure

Basic Module Layout

A module is simply a directory with Terraform files. Here's the simplest structure:

my-module/
├── main.tf # Resource definitions
├── variables.tf # Input parameters
├── outputs.tf # Return values
└── README.md # Documentation

What Each File Does

File Purpose Example Content
main.tf Actual resource definitions (VPC, EC2, RDS, etc.) resource blocks that create AWS resources
variables.tf Input variables (parameters the module accepts) variable "vpc_cidr" { default = "10.0.0.0/16" }
outputs.tf Outputs (values the module returns) output "vpc_id" { value = aws_vpc.main.id }
README.md Documentation (how to use the module) Module description and usage examples

Creating Your First Module

Step 1: Create the Module Structure

Create a directory for your module:

mkdir -p terraform/modules/aws_vpc
cd terraform/modules/aws_vpc

Step 2: Create variables.tf

This file defines what parameters users can pass to your module:

# File: variables.tf
# These are the inputs to our module

variable "vpc_cidr" {
  description = "CIDR block for VPC"
  type        = string
  default     = "10.0.0.0/16"
}

variable "environment" {
  description = "Environment name (prod, staging, dev)"
  type        = string
  default     = "dev"
}

variable "enable_nat_gateway" {
  description = "Enable NAT Gateway for private subnets?"
  type        = bool
  default     = false
}

variable "tags" {
  description = "Tags to apply to all resources"
  type        = map(string)
  default = {
    Environment = "dev"
    ManagedBy   = "Terraform"
  }
}

Step 3: Create main.tf

This file actually creates the resources:

# File: main.tf
# The actual resource definitions

# Create VPC
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-vpc"
    }
  )
}

# Create Internet Gateway
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-igw"
    }
  )
}

# Create Public Subnet
resource "aws_subnet" "public" {
  vpc_id                  = aws_vpc.main.id
  cidr_block              = "10.0.1.0/24"
  availability_zone       = data.aws_availability_zones.available.names[0]
  map_public_ip_on_launch = true

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-public-subnet"
    }
  )
}

# Create Private Subnet
resource "aws_subnet" "private" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.0.10.0/24"
  availability_zone = data.aws_availability_zones.available.names[0]

  tags = merge(
    var.tags,
    {
      Name = "${var.environment}-private-subnet"
    }
  )
}

# Fetch available AZs
data "aws_availability_zones" "available" {
  state = "available"
}

Step 4: Create outputs.tf

This file defines what the module returns to the caller:

# File: outputs.tf
# These are the outputs - what the module returns

output "vpc_id" {
  description = "The ID of the VPC"
  value       = aws_vpc.main.id
}

output "public_subnet_id" {
  description = "The ID of the public subnet"
  value       = aws_subnet.public.id
}

output "private_subnet_id" {
  description = "The ID of the private subnet"
  value       = aws_subnet.private.id
}

output "internet_gateway_id" {
  description = "The ID of the Internet Gateway"
  value       = aws_internet_gateway.main.id
}

Step 5: Create README.md

Document how to use your module:

# VPC Module

Creates an AWS VPC with public and private subnets.

## Usage

```hcl
module "vpc" {
  source = "./modules/aws_vpc"

  vpc_cidr    = "10.0.0.0/16"
  environment = "production"
  
  tags = {
    Owner = "DevOps Team"
  }
}
```

## Inputs

- `vpc_cidr` - CIDR block for VPC (default: "10.0.0.0/16")
- `environment` - Environment name (default: "dev")
- `enable_nat_gateway` - Enable NAT Gateway (default: false)
- `tags` - Tags to apply to resources

## Outputs

- `vpc_id` - VPC ID
- `public_subnet_id` - Public subnet ID
- `private_subnet_id` - Private subnet ID

Using Modules in Your Code

Basic Module Usage

Now that you've created a module, use it in your main Terraform code:

# File: main.tf (in your project root)
# This is where you USE the module you created

module "vpc" {
  source = "./modules/aws_vpc"

  vpc_cidr    = "10.0.0.0/16"
  environment = "production"
  
  tags = {
    Owner = "Infrastructure Team"
  }
}

# Access outputs from the module
resource "aws_instance" "web" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"
  subnet_id     = module.vpc.public_subnet_id

  tags = {
    Name = "web-server"
  }
}
Key syntax: module.vpc.public_subnet_id means: "Take the public_subnet_id output from the vpc module"

Using Multiple Instances of the Same Module

Use the same module multiple times with different configurations:

# Create VPC for production
module "vpc_prod" {
  source = "./modules/aws_vpc"

  vpc_cidr    = "10.1.0.0/16"
  environment = "production"
}

# Create VPC for staging
module "vpc_staging" {
  source = "./modules/aws_vpc"

  vpc_cidr    = "10.2.0.0/16"
  environment = "staging"
}

# Create VPC for development
module "vpc_dev" {
  source = "./modules/aws_vpc"

  vpc_cidr    = "10.3.0.0/16"
  environment = "dev"
}

Now you have three complete VPCs with just 30 lines of code instead of 300!

Input Variables (Module Parameters)

Types of Variables

# String variable
variable "environment" {
  type    = string
  default = "dev"
}

# Number variable
variable "instance_count" {
  type    = number
  default = 2
}

# Boolean variable
variable "enable_monitoring" {
  type    = bool
  default = true
}

# List variable
variable "availability_zones" {
  type    = list(string)
  default = ["us-east-1a", "us-east-1b"]
}

# Map variable
variable "tags" {
  type = map(string)
  default = {
    Owner       = "DevOps"
    Environment = "Production"
  }
}

# Object variable (complex type)
variable "instance_config" {
  type = object({
    instance_type = string
    volume_size   = number
    environment   = string
  })
  default = {
    instance_type = "t3.micro"
    volume_size   = 20
    environment   = "dev"
  }
}

Making Variables Required

# This variable MUST be provided (no default)
variable "database_password" {
  type        = string
  description = "Master password for RDS database"
  
  # No default = required
}

# Usage:
module "database" {
  source = "./modules/rds"
  
  database_password = "SuperSecretPassword123!"
}

Module Outputs

Returning Values from Modules

Outputs allow your module to return data that other parts of your code can use:

# File: modules/database/outputs.tf

output "database_endpoint" {
  description = "Database connection endpoint"
  value       = aws_db_instance.main.endpoint
}

output "database_id" {
  description = "Database identifier"
  value       = aws_db_instance.main.id
}

output "database_port" {
  description = "Database port"
  value       = aws_db_instance.main.port
}

output "database_name" {
  description = "Database name"
  value       = aws_db_instance.main.name
}

Using Module Outputs

# Use outputs from database module
module "database" {
  source = "./modules/database"
  
  db_name = "myapp"
}

# Now use the outputs
resource "aws_instance" "app" {
  ami           = "ami-0c55b159cbfafe1f0"
  instance_type = "t3.micro"

  # Access database endpoint from module output
  environment = [
    {
      name  = "DB_ENDPOINT"
      value = module.database.database_endpoint
    }
  ]
}

Real-World Example: VPC Module

Scenario

You need to create VPCs for 3 environments (prod, staging, dev) with consistent configurations.

Solution with Module

terraform/
├── modules/
│ └── aws_vpc/
│ ├── main.tf
│ ├── variables.tf
│ ├── outputs.tf
│ └── README.md
├── environments/
│ ├── prod.tf
│ ├── staging.tf
│ └── dev.tf
└── main.tf

modules/aws_vpc/main.tf

# Create VPC
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    Name        = "${var.environment}-vpc"
    Environment = var.environment
  }
}

# Create public subnet
resource "aws_subnet" "public" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.${var.vpc_third_octet}.${count.index}.0/24"
  availability_zone = data.aws_availability_zones.available.names[count.index]
  map_public_ip_on_launch = true

  tags = {
    Name = "${var.environment}-public-subnet-${count.index + 1}"
  }
}

# Create private subnet
resource "aws_subnet" "private" {
  count             = 2
  vpc_id            = aws_vpc.main.id
  cidr_block        = "10.${var.vpc_third_octet}.${count.index + 10}.0/24"
  availability_zone = data.aws_availability_zones.available.names[count.index]

  tags = {
    Name = "${var.environment}-private-subnet-${count.index + 1}"
  }
}

# Internet Gateway
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "${var.environment}-igw"
  }
}

# NAT Gateway for private subnet internet access
resource "aws_eip" "nat" {
  count  = var.enable_nat ? 1 : 0
  domain = "vpc"

  depends_on = [aws_internet_gateway.main]

  tags = {
    Name = "${var.environment}-nat-eip"
  }
}

resource "aws_nat_gateway" "main" {
  count         = var.enable_nat ? 1 : 0
  allocation_id = aws_eip.nat[0].id
  subnet_id     = aws_subnet.public[0].id

  tags = {
    Name = "${var.environment}-nat-gw"
  }

  depends_on = [aws_internet_gateway.main]
}

# Get available AZs
data "aws_availability_zones" "available" {
  state = "available"
}

modules/aws_vpc/variables.tf

variable "vpc_cidr" {
  description = "CIDR block for VPC"
  type        = string
}

variable "vpc_third_octet" {
  description = "Third octet of VPC CIDR (10.X.0.0/16)"
  type        = number
}

variable "environment" {
  description = "Environment name"
  type        = string
}

variable "enable_nat" {
  description = "Enable NAT Gateway?"
  type        = bool
  default     = false
}

modules/aws_vpc/outputs.tf

output "vpc_id" {
  value = aws_vpc.main.id
}

output "public_subnet_ids" {
  value = aws_subnet.public[*].id
}

output "private_subnet_ids" {
  value = aws_subnet.private[*].id
}

environments/prod.tf

Best Practices

1. Keep Modules Focused

Each module should do one thing well. Don't create one giant module for everything.

✅ GOOD: Separate modules for VPC, EC2, RDS, Security Groups

module "vpc" {
  source = "./modules/vpc"
}

module "rds" {
  source = "./modules/rds"
}

module "security_group" {
  source = "./modules/security_group"
}

❌ BAD: One module trying to do everything

module "everything" {
  source = "./modules/everything"
  # VPC, RDS, EC2, Load Balancer, Monitoring, etc.
}

2. Always Document Your Modules

# modules/my_module/README.md

# My Module

## What it does
Creates a security group allowing HTTP/HTTPS traffic

## Usage
```hcl
module "web_sg" {
  source = "./modules/security_group"
  
  vpc_id = aws_vpc.main.id
  name   = "web-sg"
}
```

## Inputs
- vpc_id (required): VPC ID where SG is created
- name (required): Name of security group

## Outputs
- id: Security group ID

3. Use Descriptive Variable Names

✅ GOOD
variable "database_instance_type" { }
variable "enable_encryption" { }
variable "backup_retention_days" { }

❌ BAD
variable "db_type" { }
variable "encrypt" { }
variable "backup_days" { }

4. Add Type Constraints

✅ GOOD: Type specified
variable "instance_count" {
  type = number
  description = "Number of instances"
}

❌ BAD: No type constraint
variable "instance_count" {
  description = "Number of instances"
}

5. Set Sensible Defaults

variable "environment" {
  type    = string
  default = "dev"
  description = "Environment (dev, staging, prod)"
}

variable "enable_monitoring" {
  type    = bool
  default = true
  description = "Enable CloudWatch monitoring"
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
  description = "EC2 instance type"
}

6. Use Consistent Naming

✅ GOOD: Consistent naming
resource "aws_vpc" "main" { }
resource "aws_subnet" "main" { }
resource "aws_security_group" "main" { }

❌ BAD: Inconsistent naming
resource "aws_vpc" "vpc" { }
resource "aws_subnet" "subnet_one" { }
resource "aws_security_group" "sg" { }

Common Mistakes to Avoid

❌ Mistake 1: Hardcoding Values
Don't hardcode values that should be variables. 
❌ DON'T DO THIS:
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"  # Hardcoded!
}

✅ DO THIS INSTEAD:
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr  # Use variable
}
❌ Mistake 2: No Descriptions
Always add descriptions to variables and outputs. 
❌ Confusing:
variable "x" { }
output "y" { value = aws_instance.main.id }

✅ Clear:
variable "instance_type" {
  description = "EC2 instance type"
  type        = string
}
output "instance_id" {
  description = "ID of the created EC2 instance"
  value       = aws_instance.main.id
}
❌ Mistake 3: Creating Huge Modules
Don't put everything in one module. 
❌ 500-line module doing everything

✅ Separate, focused modules
- modules/vpc/
- modules/rds/
- modules/ec2/
- modules/security_group/
❌ Mistake 4: Not Testing Modules
Test your modules with different variable values. 
✅ Create test configurations:
test/
├── minimal_config.tf    # Use all defaults
├── full_config.tf       # Override all variables
└── edge_cases.tf        # Test boundary conditions

Advanced Topics

1. Module Versioning

Use Git tags or Terraform module registry for versioning:

# Source from GitHub with version tag
module "vpc" {
  source = "git::https://github.com/myorg/terraform-aws-vpc.git?ref=v1.2.0"

  vpc_cidr = "10.0.0.0/16"
}

# Source from Terraform Registry
module "vpc" {
  source = "terraform-aws-modules/vpc/aws"
  version = "~> 3.0"

  vpc_cidr = "10.0.0.0/16"
}

2. For_each for Multiple Resources

Create multiple instances with different configurations:

variable "subnets" {
  type = map(string)
  default = {
    public-1a  = "10.0.1.0/24"
    public-1b  = "10.0.2.0/24"
    private-1a = "10.0.10.0/24"
    private-1b = "10.0.11.0/24"
  }
}

resource "aws_subnet" "main" {
  for_each = var.subnets

  vpc_id     = aws_vpc.main.id
  cidr_block = each.value

  tags = {
    Name = each.key
  }
}

3. Conditional Resources

Create resources only when needed:

variable "enable_nat_gateway" {
  type    = bool
  default = false
}

# NAT Gateway created only if enable_nat_gateway = true
resource "aws_nat_gateway" "main" {
  count = var.enable_nat_gateway ? 1 : 0

  subnet_id = aws_subnet.public[0].id

  tags = {
    Name = "nat-gateway"
  }
}

4. Module Composition (Modules Using Modules)

Create higher-level modules that use other modules:

# modules/complete_infrastructure/main.tf
# This module uses other modules

module "vpc" {
  source = "../vpc"
  vpc_cidr = var.vpc_cidr
}

module "security_group" {
  source = "../security_group"
  vpc_id = module.vpc.vpc_id
}

module "rds" {
  source           = "../rds"
  vpc_id           = module.vpc.vpc_id
  security_group_id = module.security_group.id
}

Key Takeaways

Remember:
  • ✅ Modules = reusable infrastructure code
  • ✅ Every module needs: main.tf, variables.tf, outputs.tf, README.md
  • ✅ Use variables to make modules flexible
  • ✅ Use outputs to share data with other parts of code
  • ✅ Keep modules focused and well-documented
  • ✅ Test modules with different configurations
  • ✅ Use modules to maintain consistency across projects

Next Steps

  1. Create a simple module - Start with a security group or VPC
  2. Document it well - Add clear README and variable descriptions
  3. Use it in a project - Apply the module to real infrastructure
  4. Reuse it - Use the same module in multiple projects
  5. Maintain it - Keep documentation and code updated
Pro Tip: Start collecting your modules in a modules/ directory. As you build more infrastructure, you'll accumulate a library of reusable components that make future projects much faster!
